通俗解释

什么是 WebSocket

HTTP 像打电话——你说一句，对方答一句，说完就挂；WebSocket 像面对面聊天——双方随时开口，话筒始终在线。

📞
HTTP · 半双工

打电话模式

每次都要先拨号建立连接（请求），听完对方回答后挂断。想再问？重新拨号。每次都要带上完整的"身份头"（Cookie、UA 等），开销大，无法主动接收信息。

👥
WebSocket · 全双工

面对面聊天

只需一次"握手"建立连接，之后双方随时可以同时开口。轻量级数据帧（2~10 字节头），服务器可以主动推送，连接持久保持，实时性极高。

技术选型

HTTP vs WebSocket vs SSE

三者各有定位，点击下方 Tab 高亮对应列，理解每种技术的优势与局限。

💡 经验法则：只需要服务器推消息（如股票行情）选 SSE；需要双向实时交互（如聊天、游戏）选 WebSocket；普通请求响应用 HTTP 即可。

实战场景

核心应用场景

凡是需要"服务器主动推送"或"低延迟双向交互"的场景，几乎都是 WebSocket 的主场。

💬实时聊天

消息即时送达、已读回执、在线状态同步。微信网页版、Slack、Discord 等均基于 WebSocket。

🎬直播弹幕

百万级并发弹幕下发，WebSocket 推送比轮询节省 90% 带宽，延迟低于 200ms。

📊实时数据监控

服务器 CPU、IoT 传感器、股票行情持续推送，前端图表平滑滚动更新。

📝协同办公

多人同时编辑文档（飞书、Notion），光标位置、文本变更通过 WebSocket 实时广播。

🎮在线游戏

多人对战的位置同步、技能释放，每秒数十次双向通信，WebSocket 提供稳定低延迟通道。

🤖AI 流式输出

大模型逐 Token 流式返回，ChatGPT、Claude 网页版通过 WebSocket 或 SSE 实现"打字机"效果。

可靠性

心跳与重连机制

TCP 无法立即感知对端断开，需要应用层心跳保活；连接异常断开后，指数退避重连可避免雪崩。

生产实践

安全注意事项

WebSocket 不受同源策略自动保护，生产环境必须额外加固。

🔒

wss 加密传输

务必使用 wss:// 而非 ws://。wss 基于 TLS，防止中间人窃听和篡改，等同于 HTTPS 对 HTTP 的意义。

🛡️

Origin 校验

浏览器会自动带上 Origin 头，服务端必须校验白名单，防止跨站 WebSocket 劫持（CSWSH）攻击。

⏱️

限速与鉴权

握手阶段校验 Token / Cookie，连接后限制单连接消息频率和总连接数，防止恶意刷消息压垮服务器。
