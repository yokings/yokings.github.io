A

总体判断与优先风险

具备清晰的记忆后端主干，生产可靠性仍有缺口

项目采用模块化单体，分离采集、异步生成和只读查询。 来源修订、日记版本与血缘构成了较好的可审计基础。 目前最应优先处理安全入口、删除传播和派生版本一致性。

优先级 主要问题 本次证据
P0 数据库凭据写在源码中；旧 HTTP 接口绕过鉴权 配置静态检查；旧路由函数直接返回私有测试日记
P1 来源删除后残留实体观察；周期总结不会随日记修订更新 内存端到端复现
P1 长任务缺少续租与写入隔离；生产入口接线不完整 Worker、Repository 与 FC 代码检查
P1 多来源对账混入其他来源；低预算仍可超量返回 内存与预算函数复现

定位：为摄像头和聊天智能体提供长期背景记忆。 主链路消费上游摘要和结构化记录，再提炼领域信息。 它适合近期回顾、场景先验和规律提示。 精确问答召回、真实身份识别和完整视频理解仍有边界。

本报告分析当前工作区，包含原有未提交文件。 检查期间没有修改业务代码，也没有连接生产数据库。 报告没有复制源码中的凭据。

B

架构如何分层

层 主要模块 职责
接入层 api/fastapi_app.py、api/fc_handler.py、contracts.py HTTP、FC 事件、参数契约与服务令牌
编排层 service.py、job_runner.py 注入依赖，组织采集、处理、查询与周期任务
来源层 sources/collector.py、mysql_adapter.py、reconciler.py 来源映射、游标、只读扫描与快照对账
记忆领域层 journal/writer.py、consolidation.py、memory_query.py 日记生成、分层压缩、背景上下文
视觉领域层 entity/、scene_profile.py、activity_rhythm.py、household/ 匿名实体、事件、场景、规律与家庭画像
基础设施层 storage/、core/、observability/ MySQL、模型调用、媒体签名、日志与指标
回放与辅助层 sim/、scripts/、video_down/、media_extract/ 数据回放、云端拉取、浏览器工具与独立抽帧包

这些层共用一个代码库，通过不同入口执行不同角色。 持久化 Job 表承担内部队列功能。 当前主链路没有依赖 Celery、Redis 或向量数据库。 JournalService 可注入 Repository 和 LLM，便于离线验证。

media_extract 是独立辅助包，依赖 SEI 与本地 C 库抽帧。 它尚未直接接入 JournalService 的默认处理链路。 不能将其存在等同于主链路已经理解完整视频。

C

核心技术方案与数据生命周期

方案 实现机制 价值与取舍
自主采集 (updated_at, primary_key) 排序；重叠窗口；映射版本；坏记录隔离 重扫可幂等；依赖来源正确维护更新时间和软删除
事务型任务入队 来源 revision、Job、checkpoint 同事务提交 避免游标已推进但任务没有持久化
追加式证据账本 source head 指向当前修订；journal entry 指向当前日记版本 可追溯、可回查；旧表仍承担兼容投影
全日 canonical rebuild 从当前来源集合重建，不把旧摘要当唯一输入 减少增量摘要漂移；LLM 正文仍有随机性
长日分块 默认每块 80 条，另有字符上限；记录覆盖 ID 与输入 digest 可检查输入无遗漏；覆盖完整不等于事实正确
模型与确定性规则配合 LLM 写摘要；代码补写实体、事件、时段和画像字段 结构化事实更可控；多模块仍须保持版本一致
分层压缩 日到周、月、年；缺失下层时回退取源；不足证据限制趋势 降低长期上下文体积；必须同步传播修订与删除
只读组装 默认取 7 日、4 周、6 月、2 年；支持 as_of 查询不触发生成；选择依据主要是时间与层级
证据成熟度 cold / warming / ready；检查天数、时段和采集完成比例 抑制样本不足时的长期结论
模型故障处理 Qwen 默认；兼容其他厂商；超时看门狗、退避与静态回退 提高链路可用性；回退结果必须显式降级

数据库结构以三条关系为核心：

  • journal_source_record → journal_source_record_revision：同一原子来源的历史修订。
  • journal_entry → journal_revision：同一日期和层级的日记版本。
  • journal_lineage：关联日记与来源修订，或关联上下层日记版本。

实体、样本、事件、场景、规律和用户画像另有领域表。 MySQL 是权威存储，媒体通过引用和临时签名访问。 as_of 查询按版本创建时间选择当时已知的日记。 当前实现并不保证所有派生字段都遵守相同历史边界。

依据：sources/collector.py:44、storage/mysql_repos.py:1909。 生成依据：journal/writer.py:285、storage/mysql_repos.py:249。 查询依据：journal/memory_query.py:26、storage/mysql_repos.py:684。 本页简称路径均相对 journal_service/，除非另有说明。

D

当前实现了哪些功能

功能 核心实现 能力边界
Vision 日记 常驻目标、事件、变化、噪声、异常与摘要 主输入是上游摘要；无法覆盖摄像头未上报的时段
Chat 日记 对话片段、事实、偏好、计划、未决事项与纠正 数据组织以日日记为单位；没有独立事实召回接口
匿名实体追踪 文本分词相似度、区域、时间与视觉向量融合 设备内候选关联；不是人脸身份识别
视觉 ReID 开放词汇定位 → 裁剪 → embedding → 样本中心比较 配置缺失或调用失败时退回文本；阈值须真实评测
实体纠错与生命周期 候选晋升、失活、退休；视觉样本驱动合并和拆分 不能把实体 ID 数直接解释为真实人数或宠物数
事件校准与时段画像 按事件类型合并时间窗；统计四个时段 时间窗是规则近似；不是完整视频中的精确动作边界
图片复核 稀疏高优先级抽查；逐项 claims 与审计账本 单帧不能证明速度和完整行为过程
场景画像 固定锚物、区域、类别、质量与空间信息 两段式判断视角切换；当日视觉缓存仍须修订治理
规律活动识别 日直方图、活跃/低谷窗口、时间锚点与周期判定 输出是统计规律；受来源覆盖和实体错误影响
家庭用户画像 汇总多设备宠物、人员、车辆及外观先验 保留证据边界；数量估计不等于真实身份统计
主动感知 场景切换、实体变化、未见、规律偏离和计划到期 当前写入 attention 清单；不等同于已接通消息推送
版本化查询 Memory 包、日记历史、血缘、实体时间线和用户先验 FastAPI 与 FC 的路由覆盖尚不一致

视觉关联存在灰区融合、高置信覆盖和视觉否决三个路径。 样本与 Observation 同事务保存，来源修订可使样本失效。 场景切换会抑制跨日的人物与宠物纯文本合并。 这些设计有助于减少错误的身份连续性判断。

规律模块采用确定性统计发现，再用 LLM 命名或裁决异常。 场景、规律与关怀提示失败时，日记生成通常继续运行。 这是可用性策略，但必须同时暴露组件降级状态。

记忆一致性与预算问题

编号 触发条件 实际行为与影响 代码位置
F1 · P1 来源删除，或修订将记录移出原日期/设备 Matcher 只遍历当前来源；消失的来源不会进入失效集合。旧 Observation 与样本可能继续影响画像。 service.py:372、entity/matcher.py:269、entity/matcher.py:346
F2 · P1 成功压缩后修正历史日记或补入迟到数据 Consolidator 永久跳过 status=ok 周期。日记已更新，长期总结仍引用旧版本。 journal/consolidation.py:243
F3 · P1 任务超过租约，或同设备任务并行 一次领取整批任务；租约默认 5 分钟，没有续租、领取代次校验和设备写锁。旧 Worker 可晚于新 Worker 写入。 service.py:175、core/config.py:523、storage/mysql_repos.py:569
F4 · P1 同一用户设备同日注册两个来源 对账输入属于单来源，但当前集合包含全部来源。另一来源被误判为额外记录。 sources/reconciler.py:29
F5 · P1 预算很低，必须保留的摘要较多 摘要保留条数和 240 字符下限使裁剪提前退出。字符预算也不是真实 token 上界。 journal/memory_query.py:612、journal/memory_query.py:658
F6 · P2 查询历史 revision 或重新处理过去日期 attention 从最新兼容表合入；规律快照查询没有日期上界。历史结果可能混入更新的信息。 storage/mysql_repos.py:721、storage/mysql_repos.py:1771、journal/activity_rhythm.py:1334

F1 复现： 先写入一个人物观察，再删除其唯一来源。 Worker 返回 completed，当前来源数量变为 0。 当前 Observation 数量仍为 1。 应按旧来源引用清理派生记录，并重算受影响画像。

F2 复现： 先生成完整周总结，再修正其中一天。 再次执行压缩，重建周数为 0，周 revision 未变化。 建议以输入版本指纹判断更新，并逐层传播 dirty 状态。

F3 推演： A 读取旧来源后运行超过租约。 B 重领任务或处理同设备新任务，写入更新结果。 A 最后完成，可以把旧结果再次设为 current。 行锁只保证版本编号递增，无法保证输入新旧顺序。 建议加入续租、fencing token、输入版本检查和设备串行化。 仅同日串行不足以保护跨日共享的场景与实体主档。

F4 复现： 来源 A、B 各写入一条相同日期记录。 只对账 A，结果为 partial，extra_ids 含 B 的记录。 应先按来源过滤，再汇总 required/optional 来源状态。 不同来源的相同记录 ID 也需要命名空间隔离。

F5 复现： 给 3 条摘要设置 512 字符预算。 裁剪返回 1099 字符，且 truncated=false。 用户级投影还会为每设备保留最低预算，缺少总量二次裁剪。 建议将预算设为硬边界，并处理最低信息也装不下的情况。

F6 静态证据： 历史日记内容按 revision 截止时间选择。 attention 却按日期补读最新兼容投影，没有核对 revision。 规律模块读取 eval_date >= since_day，未限制结束日期。 重算历史日时，未来快照可能进入统计。 场景当日 VLM 缓存也没有校验来源输入指纹。 建议统一事件时间、系统版本时间和派生输入版本。

六项中，F1、F2、F4、F5 已通过内存或函数复现。 F3、F6 基于代码路径确认风险，未做真实并发数据库压测。

G

生产化与功能边界

方面 当前状况 影响与下一步
日终对账调度 正式 Service 只读取对账状态；实际快照对账主要由 sim/journal.py 编排 Collector 成功不等于 final；需要正式日终调度和关窗规则
完整性口径 required/optional 汇总不足；日记写入时缺失来源清单固定为空 不能将空清单解释为全部来源可用
历史来源捕获 Collector 只支持 polling_current_state 硬删除或两次扫描间的中间修订可能不可见；需要软删除或 CDC
读取规模 查询从 1970 年读取全部历史，再在 Python 取最后 N 条 响应大小有限，数据库读取量仍随历史增长；下推 LIMIT 和时间窗口
周期调度规模 list_tenants 默认最多 1000，无分页；全量压缩串行 超出上限的作用域可能长期不处理；按作用域分页入队
降级可见性 场景、纠错、规律和家庭画像错误通常只记日志 completed 不表示所有组件可用；增加组件质量状态与重试任务
问题驱动召回 请求不接受具体问题，主要按固定时间层级选择 背景记忆适用；“上次何时发生”可能需要独立 Recall API
数据权利与反馈 来源修订已有基础；反馈、删除屏障等仍未形成完整流程 不能宣称完整用户纠错和删除能力已验收
发布复现 requirements 未锁版本；README 迁移清单只列到 009 当前迁移已有 016；需要统一发布清单、依赖版本和启动说明
可观测性 进程内低基数指标；未见完整 exporter 与 SLO 接入 需观测队列滞后、租约、来源完整性、模型成本及降级比例

查询层当前没有关键词、语义向量、融合排序或重排链路。 ReID embedding 用于视觉个体关联，不是记忆文本召回。 建议先增加可重建的原子记忆读模型，再按问题检索。 继续保留 revision 和 lineage 作为证据真相源。 引入向量服务应以真实问答集收益为依据。

旧效果报告不能直接作为当前版本的验收结果。 2026-09-11 报告记录过文本过度合并与复核质量问题。 当前代码已加入视觉 ReID、场景切换和统计纠错。 这些改进的真实效果需要重新标注和回放评测。

报警摘要覆盖率也不能代表连续视频覆盖率。 缺少记录可能来自设备离线、未触发或采集失败。 弱信号中的“未见”需要明确证据条件。
