A

整个系统最终在做什么

不只是生成一段摘要，而是建立可追溯的记忆账本

云端视频描述先成为来源证据，再成为实体、事件和日记。 跨天历史进一步形成规律、场景和家庭画像。 最后，查询接口把已存储的版本组装成结构化 Memory 包。 这里的“记忆”存放在数据库中，不是重新训练模型权重。

本页以你当前使用的 action=sim_pipeline 为主线。 默认域是 vision，对应 R1 日记，作用域是用户、设备和自然日。 chat 对应 R2，作用域是用户，内部设备键使用 _。 聊天接入支路在 B、G、H 中单独说明。

最终成果分为四类，而不是只有一个返回字符串。

成果 给谁使用 是否持久化
日日记及周、月、年总结 记忆查询、展示、历史复盘 MySQL 保存当前版本和历史修订
实体、场景、规律、家庭画像 长期识别、上下文先验与变化检测 对应主档和日快照表
Memory 包与用户级投影 下游对话或业务调用方 查询时组装；sim 另导出 JSON
证据账本和运行报告 定位遗漏、解释推断和审计 MySQL 账本；本地导出文件

这是按源码整理的调用图，不是某次云端调用的真实运行轨迹。 开关、依赖失败和空数据会改变实际执行分支。 本次没有连接云端或读写业务数据库。

本次同步到 dev 的 700d8ca。 对比基线为 5da4c23，新增变化来自 d7a2629 和 700d8ca。 FC、云端拉数、Collector 和 Memory 查询主链路没有变化。 变化集中在语义判断，不是替换整套存储或采集架构。

B

从 FC 开始，函数按什么顺序调用

入口解析与分流 入口文件是 journal_service/api/fc_handler.py。

handler(event, context)
  • 解析 bytes / str JSONFC 事件转成字典
  • Timer 解包 payload未指定 action 时默认 consolidate_all
  • HTTP 信封分流有 path 或 method 时进入 _handle_http
  • _handle_event(event)根据 action 分发

sim 事件依次进入 _handle_sim_action() 和 _run_sim_pipeline()。 这条分支提前分流，不调用默认 _svc()。 _run_sim_pipeline(prepare, writer, journal, params) 串行调用三个阶段。

① prepare：云端拉数和按天落盘

sim.prepare.run(params)
  • _apply_cloud_env()配置视频接口使用的运行时环境
  • _resolve_device_sns()显式设备优先，否则拉设备列表
  • collect_device_videos()downloader 模块；逐设备拉视频描述与详情
  • map_to_table_row()生成动态表字段
  • _select_latest_window()可选保留最近自然日

② writer：把准备数据写入动态表

sim.writer.run(params)
  • load_exp()读 meta.json 和日期列表
  • write_day()逐天 INSERT IGNORE
  • update_cursor()记录本实验已写日期

③ journal：记忆加工与导出

sim.journal.run(params)
  • _validate_params()域、用户、设备、模型凭据等校验
  • UserBoundSourceAdapter()创建 adapter，继承 MySQLPollingSourceAdapter
    • 连接解析器_connection_resolver；按 connection_ref 连接来源库
    • 设备用户绑定binding={sn: user_id for sn in device_sns}
    • 首次扫描起点since=cfg["since"]；已有 checkpoint 时按游标回扫
  • JournalService()注入 source_adapter=adapter，单独创建服务
  • register_source()登记选定域的 SourceDefinition
  • SourceCollector()传入 service.repo、同一 adapter 和 page_size=100
    • collect(source)对每个 ready 来源分页采集
      • stable_upper_bound()Collector 调 adapter，取得扫描时间上界
      • fetch_page()Collector 调 adapter，逐页读取来源表
  • _snapshot_source()同一 adapter 扫描来源历史快照，再交给对账器
  • reconcile_scope()SourceReconciler；按设备和自然日对账
  • process_pending_jobs(limit=10)循环直到当前无可领取任务
    • _process_day_job(job)执行一个日级任务，详见 E、F
  • 生命周期维护run_entity_lifecycle_maintenance()；仅 lifecycle=true
  • consolidate_all()未设置 skip_consolidate 时执行
  • assemble_memory()每设备和用户级只读查询
  • 导出 JSONjournals / memory / evidence / run

adapter 在这里连接哪两部分？ 它连接 Collector 和来源 MySQL，不连接 FC 和云端视频接口。 writer 先把 prepare 数据写进动态表，adapter 再从表中读出。 adapter 按设备过滤，给 vision 行补 user_id，并清洗 SQL 字段值。 首次读取可用 since；后续读取使用 checkpoint 和分页游标。

对象 负责什么 不负责什么
SourceDefinition 指定表、字段映射、时间列和 connection_ref 不自行连接数据库
_connection_resolver 把 dev_algorithm 解析为来源库连接 不确定采集游标，不保存记忆
UserBoundSourceAdapter 读取上界与来源行，做设备过滤及用户绑定 不下载云端 JSON，不写日记
SourceCollector 调用 adapter、映射行、去重和推进 checkpoint 不生成实体语义或日记摘要
service.repo 保存来源修订、Job、checkpoint 等记忆账本 不代替来源 adapter 拉取动态表

同一个 adapter 既注入 JournalService，也直接传给 SourceCollector。 当前 sim 直接创建 Collector，不绕经 service.collect_sources()。 快照读取也复用 adapter，但对账由 SourceReconciler 执行。 默认 FC _svc() 没有 adapter，不影响这条独立创建的 sim 服务。

创建与传递：sim/journal.py:506、:511、:541、:560。 读取逻辑：sim/journal.py:117、:219、sources/mysql_adapter.py:26。 Collector 调用：sources/collector.py:55、:64。

prepare → writer → journal 在同一次 FC 调用内串行执行。 sim_pipeline 缺少 user_id 时直接返回错误。 prepare 没有可写日期时，跳过 writer，但仍执行 journal。 因此“无新视频”不等于“本次不会处理任何任务”。

真实模型凭据在 journal 阶段校验。 所以可能先拉数和写动态表，再因凭据缺失而中止加工。 重试时需要分别核对写库进度、采集进度和任务状态。

pipeline 的 writer 固定使用 vision 域，不执行 truncate。 journal 默认也只处理 vision；它能读取库中已经存在的 chat 来源。 consolidate_only=true 只影响 journal 阶段。 它不会让整个 pipeline 跳过前面的 prepare 和 writer。

其他 FC 入口与主线的关系如下。

入口 起点和差异 后续去向
sim_journal 跳过云端准备和动态表写入；仍需配置用户设备 从已存在的动态表开始加工
collect_sources 使用默认 _svc()；当前未注入来源适配器 原本用于独立 Collector，不是当前 sim 路径
ingest_observations / POST /v1/observations:batch 接收外部已经标准化的事件 ingest_events() → 来源修订和 Job
process_pending_jobs 不拉云端清单，不准备动态表 直接消费已有 Job，进入同一日级加工
consolidate_all 不拉视频，不采集动态表 从已存日记生成缺失周期总结

推送接入会额外使用 journal_http_request、journal_event_inbox。 它还维护 journal_ingest_checkpoint，不是 Collector 的游标表。 不要把这条支路的中间表误认为 sim_pipeline 必经步骤。

V1 HTTP 路由先调用 authorize_service() 校验服务令牌。 sim_pipeline 事件分支不走这份 HTTP 令牌校验。 它的调用权限需要按 FC 事件入口单独核对。

依据：api/fc_handler.py:160、api/fc_handler.py:181。 入口路由：api/fc_handler.py:234、api/fc_handler.py:275。 本页代码路径除另有标注外，均相对 journal_service/。

C

什么时候拉取什么数据

这里需要区分三种“拉取”。 第一种从云平台和 OSS 获取新输入。 第二种从 MySQL 读取来源及历史记忆。 第三种把关键帧送给模型，得到定位、向量或复核结果。 新增文本裁决只读取结构化文本，不等于又下载一遍图片。

时机 函数 从哪里取 实际取得什么
prepare 开始，未指定 device_sns _resolve_device_sns() → list_user_devices() 用户设备接口 用户名下设备清单，主要消费 sn
每台设备进入准备阶段 fetch_video_description() 视频描述接口 时间窗内描述任务信息，主要消费 bodyFileUrl
bodyFileUrl 非空 get_sts_credentials() /storage-auth/api/v1/sts/info 下载 OSS JSON 的临时访问凭据；不是业务记忆
取得 STS 后 download_body_json() OSS 中 bodyFileUrl 对象 视频条目清单、extraInfo 与详情访问凭据
清单存在视频条目 enrich_with_details() → download_detail_json() OSS；命中时读本地缓存 videoDetailUrl 优先，否则 jpgDetailUrl 的详情 JSON

云端时间窗如何确定？ prepare 在当次运行时取 now，查询 [now-hours, now]。 未传 hours 时，实际默认值是 72。 pipeline 注释里的 26 不会自动覆盖这个默认值。 FC 何时启动由事件或云端定时触发器决定，项目没有内部定时器。

自然日按 JOURNAL_TIMEZONE 分桶，默认 Asia/Shanghai。 latest_days 从最新事件日向前保留 N 个自然日。 它不是“从服务器今天起向前 N 天”的固定窗口。

采集游标如何确定？ 首次没有 checkpoint 时，适配器可使用 since 作为扫描下界。 以后从 checkpoint 时间减去 overlap_seconds 开始回扫。 默认重叠 120 秒，页内按更新时间和主键排序、推进。 sim 映射把 timestamp 同时当作事件时间和更新时间。 所以“新插入数据库的老事件”不一定在增量扫描范围内。

快照对账另取时间上界，并从 1970 年下界扫描。 这不表示再次从云平台下载全部历史视频。 它只扫描已经在动态表里的历史记录。 它也不会自动补回 prepare 尚未下载的数据。

时间字段 含义 不应混淆为
event_time / timestamp 摄像头事件发生时间，决定归属自然日 FC 执行时间
source_updated_at / effective_at 来源修订的有效或更新时间 当前 sim 中独立的数据库更新时间
stable_upper_bound 本轮来源扫描的上界 平台完整性水位承诺
created_at / generated_at 账本写入或记忆版本生成时间 原始事件发生时间
as_of 查询的时间截止条件 触发重新生成记忆的时间

到底下载了视频还是描述？ prepare 主要下载 JSON 清单和描述详情，不下载录像 MP4。 录像 URL 作为 recording_url 保存，关键帧 URL 作为 high_frame_url 保存。 ReID 在需要时才下载关键帧像素，生成临时裁剪图。 视觉模型也会按签名 URL 读取选中的图片。 不是每条视频都必定经过视觉复核。

依据：video_down/downloader.py:98、:117、:159、:173、:245。 时间窗与分桶：sim/prepare.py:143、sim/journal.py:231。 增量扫描：sources/collector.py:38、sim/journal.py:117。

D

拉回来的数据如何第一次沉淀

先整理字段，再写动态表。 map_to_table_row() 从视频 id 或 ext.first_gop_time 解析事件时间。 没有 id、有效时间或可用描述的条目会被过滤。 title、abstract、description 优先来自详情 JSON 的 body。 title 和 abstract 可回退 alarmName，并各截到 250 字符。

动态表字段 来源或规则 含义
video_id 云端视频条目的 id 上游事件标识
device_sn 当前处理设备 sn 数据归属设备
timestamp id 毫秒时间或 ext.first_gop_time 带时区的事件时间
title / abstract / description 详情 JSON；部分字段可回退 alarmName 上游已有的文字描述，不是本项目刚生成的日日记
high_frame_url / recording_url picUrl / url 关键帧和录像引用，不是媒体二进制
video_score 当前固定为 3.0 映射默认值，不是真实模型评分
ominous 当前固定为 false 映射默认值，不代表已经证明无异常
source cloud_video_summary 原始数据来源标记

ts_ms 只在准备阶段排序使用，不写入日 JSON。 prepare 生成三个实验文件，再交给 writer。

SIM_DATA_DIR / exp_id
days / YYYY-MM-DD.json单日 videos 列表，chats 固定为空
meta.json用户、设备、窗口、日期和日文件摘要
cursor.jsonwritten_through 与 written_days，表示本实验写库进度

writer 逐天执行 INSERT IGNORE，目标是 bc10_video_summaries_dev。 同主键重复时跳过，不能把它当作来源内容修订的更新机制。 写完一天后提交，再更新本地 cursor。 云端窗口、writer cursor、Collector checkpoint 是三个不同概念。

Collector 再把动态行变成统一来源证据。 来源映射指定表、主键、字段和 connection_ref，不保存数据库密码。 vision 表没有 user_id 列，适配器按设备绑定注入本次 user_id。 map_source_row() 产出统一记录，包含 payload 和 content_digest。 media_refs 只提取 URL 或引用字段，不复制媒体文件。

持久化位置 中间数据含义 后续用途
journal_source_registry / journal_source_registry_head 来源映射版本及当前映射指针 决定如何读表和规范化
journal_collector_batch 已提交采集批次及结果 批次幂等，避免重交
journal_collector_revision_dedupe 来源、主键、更新时间、内容等组成的修订键 重叠回扫时识别重复
journal_collector_source_head 某来源主键当前有效内容的定位 修订排序和当前版本选择
journal_source_record 一条原始记录的逻辑身份与当前修订指针 保留记录身份，不把每次修订当新事件
journal_source_record_revision 每次接受的规范化内容和媒体引用 原始证据快照，后续日记引用它
journal_job 某域、用户、设备、自然日的加工任务 将采集与模型加工解耦
journal_internal_outbox 新任务 ready 事件 可供通知分发；当前 pipeline 直接轮询 Job
journal_collector_checkpoint 已安全提交的来源复合游标 后续增量扫描下界
journal_collection_quarantine 有路由但无法规范化的隔离记录摘要 记录映射错误，不直接进入生成
journal_reconciliation_run 期望记录与已沉淀记录的差异 判断缺失、多余、内容不一致
journal_source_manifest 某次来源快照的条数及摘要 保存对账使用的来源清单证明

无法得到有效路由或游标的行会使该次扫描报错。 能路由的映射错误可以进入 quarantine。 来源修订、Job、隔离项和 checkpoint 在一页事务内提交。 这不表示整个 pipeline 是一个大事务。

同日同 scope 的新修订会合并到 pending Job。 不会固定为“一条视频触发一次日记生成”。 有效更正、删除或归属日期变动，也可以触发对应日期重建。 但当前 sim 的 INSERT IGNORE 和 delete_column=None 限制了这类输入。

对账在 Worker 之前执行。 快照按设备和自然日分组，与当前来源记录比对主键和内容摘要。 得到 missing_ids、extra_ids、mismatched_ids。 已结束的自然日且集合一致，才标 complete；当天仍是 partial。

当前 sim 使用 snapshot_only，不是平台水位证明。 即使集合一致，通常仍是 best_effort / unverified。 对账记录差异，不自动修复缺失记录或完成再次采集。

Entity、Observation、事件不是同一个东西。 一条视频可以产生多个实体观察。 同一个 Entity 可以跨多天产生许多 Observation。 相邻视频的多个报告可以归并为一个 calibrated event。 例如相邻的投递报告，不应自动计为多个独立投递事件。 多条证据形成 confirmed 是代码的证据规则，不等于客观事实已被绝对证明。

实体作用域限定到用户和设备，没有保证跨摄像头身份统一。 视觉向量用于外观关联，不是通用文本 RAG 向量库。 没有模型凭据、图片或定位能力时，可退回文本关联。 新来源修订可产生新 Observation，并替代同来源旧观察。

文本标注现在怎样影响后续判断？ 合法且非空的 types 会筛掉模型未声明的关键词实体类型。 随后补齐模型声明但词表没识别出的候选。 types 为空或无合法类型时，仍保留词表结果。 因此模型返回空数组，不代表强制判定“没有实体”。

role 只覆盖 person，合法值为 elder、adult、child、staff、unknown。 target 是主要目标的去动作外观描述，不是 bbox 或身份标签。 ReID 优先使用 target 定位；缺失时用词表剥离动作。 多目标记录没有逐实体 target，不能保证每个候选定位描述都独立。

事件分类复用 types，不为每条记录另调分类模型。 多标签按 package → vehicle → animal → object → person 选一个事件类型。 animal 映射为 pet；时间窗归并仍由代码执行。

窗口为 package 2 分钟、vehicle 10 分钟、pet 3 分钟。 object 为 30 分钟、person 为 3 分钟；兜底 motion 为 3 分钟。

文本角色缓存版本已从 1 升到 2，旧缓存不再命中。 设备、日期、模型和文本内容共同决定缓存复用。 role 和 target 与 types 同次生成，不额外调用模型。

场景分析优先复用当日已有 VLM 结论。 否则按配置挑选关键帧，融合固定锚点、区域、画质和空间信息。 默认日限额为 1；不是对每条视频都调用场景模型。

anchors[].fixed 优先决定是否作为固定参照物。 接受布尔值和字符串 true / false；缺失或非法时回退名称词表。 该标记复用场景 VLM 输出，不额外调用一次模型。 旧日快照仍可复用，缺少 fixed 时走词表兜底。

场景关键帧仍按 video_score、ominous、时间排序。 它不同于 F 中新增的日记图片复核排序。

规律读取默认 30 天活动快照，周期指纹可另读 120 天历史。 规律名称和新增异常裁决可以调用文本模型。 统计发现仍以观察和日快照为输入，不是只看模型摘要猜规律。

提醒裁决不是让模型扫描全部视频寻找异常。 节律模块先产生统计异常，再由 LLM 保留、抑制或改写。 关怀模块先匹配策略、检查阈值和场景抑制，再交给 LLM。 模型不能增加未进入候选集的提醒，也不改变证据引用和去重键。

severity 仅接受 low、medium、high；文案限制 120 字符。 关怀文案还须包含“建议关注”或“建议查看”，并排除内部术语。 画面切换和画质信号绕过跨日冷却，仍受当天限额约束。

当前裁决请求只发送候选类型、等级和文案等摘要。 它不直接附带完整直方图、基线数值或采集覆盖状态。 因此不能把模型裁决视为已经核对全部来源完整性。

统一裁决助手如何兜底？ 新增文本裁决统一调用 core.adjudication.run_adjudication()。 它批量发送 items，通过输出 i 映射回输入 id。 关闭开关、无可用模型、调用或解析异常时返回空决策。

缺失项由调用方逐项回退；合法字段覆盖规则结果。 裁决助手允许解析重试，实际请求数不保证只有一次。

CARE_LLM_ENABLED、ANOMALY_LLM_ENABLED 默认开启。 ROLE_LLM_ENABLED、GROUNDING_QUERY_LLM_ENABLED 默认也开启。 SCENE_ANCHOR_FIXED_VLM_ENABLED 默认开启。 关怀和异常的独立模型配置默认空，复用客户端默认文本模型。 这些是源码默认值，不是已确认的 FC 环境变量。 可选裁决回退不一定把日记标记成 generation_mode=fallback。

图片签名、ReID、场景复核、日记图片复核和家庭外观描述是不同调用。 它们可能使用同一关键帧，但没有统一的“一张图只读一次”全局保证。 角色缓存、ReID 磁盘缓存和详情缓存也各有自己的开关与键。

可选模块失败时，多个分支会记录告警并继续日记生成。 因此没有某类画像或中间数据，不一定让整个 FC 调用抛异常。 process 模式会新建真实 OpenAi 客户端，不能假定继承 no_llm 替身。

F

这些数据如何生成可追溯的日日记

write_day_canonical() 先按稳定规则排序全部当日证据。 它计算 day_input_digest，再按记录数与字符数分块。 默认每块最多 80 条，字符阈值 60000；单条过长时仍可能超过阈值。 这些是代码默认值，不是已核对的云端配置。

图片复核先收集带图候选，再用文本 LLM 打 0–10 分。 模型读取 title、description、ominous，不读取图片像素。 缺项或非法分数回退规则分，整体失败则回退规则排序。 然后按排序、去重和剩余预算选择图片，交给 VLM 逐图复核。 默认预算为一轮日记构建 3 次，分块间累计 ledger。 新的全日重建并不是自动复用数据库里所有旧复核结论。

复核输出 finding、changed、claims、temporal_context 等信息。 它们既进入 prompt，也进入可审计的复核账本。 预算耗尽、重复与失败也有记录，不是凭空得到新视觉结论。

IMAGE_REVIEW_SELECT_LLM_ENABLED 默认开启。 排序在每个分块内部执行，不是对全日所有图片统一排序。 前块可能先用完预算，后块的高分图未必能复核。 预算耗尽时仍可能调用排序模型；0 分也不是排除候选的硬门槛。 3 次预算限制的是图片复核，不是整条流水线所有模型调用。

图文冲突如何消解？ 只处理成功图片复核中 verdict=contradicted 的可见事实主张。 图片不能推翻来源的 capture_time 等时间字段。 _claim_match_resolver() 批量配对主张与日记条目或摘要句。 文本 LLM 判定是否为同一事实，缺项时回退同义词和子串匹配。 CLAIM_MATCH_LLM_ENABLED 默认开启，输出 match 必须是布尔值。

程序仅移除匹配条目中被否定的来源引用。 证据数降到零才移除整个结构化条目。 若条目被移除且无保留条目支持该主张，再清理匹配摘要句。

known_noise_sources 保存图文冲突，meta 保存 image_evidence_constraints。 冲突处理不修改原始来源修订，也不重写已落库的 Entity 或事件。 分块生成后和全日合并后都可能执行裁决，没有全局复用保证。 日记复核排序和冲突匹配的模型配置默认空，复用默认文本模型。

prompt 包含文本记录、复核结论和可用实体、事件、时段、场景、规律。 R1 的部分字段由代码计算并在生成后回填。 不是让模型自由发明 entity_id 或替代校准事件。 代码回填字段也可能依赖前面的模型判断，不代表完全不依赖模型。 符合确定性 R1 条件时，各块独立生成语义增量，再由代码合并。 模型失败时用静态摘要回退，并标记内容降级。

相同文本可以在 prompt 中合并，减少重复输入。 但各条来源修订仍保留在覆盖账本中，不因此丢弃证据引用。

几个“完成”标记必须分开理解。

标记 判断的对象 当前含义

分块 ledger 会检查缺失来源修订和重复覆盖。 它证明输入进入生成流水线，不证明摘要忠实表达了全部细节。 当天通常是 partial_final，因为自然日仍未结束。 对账 complete 也不等于上游视频平台承诺没有遗漏。

新增或更正来源可以触发新的全日日记修订。 已有 status=ok 的周期总结却不会因此自动全部重压。 所以“日日记修正”不代表“全部长期总结已同步修正”。

周期调用的实际补压顺序是 month → week → year。 不是简单按 day → week → month → year 顺序调用函数。 月总结先看这一轮运行前已经存在的周总结。 年总结可以复用同轮补出的月总结。

默认补缺回看范围：周 8 个、月 13 个、年 3 个。 只处理已结束的对应自然周期；没有任何来源时跳过。 status=ok 的周期被认为已完成，不自动重复压缩。 fallback 周期可以在后续补压重试。

period_coverage 保留 covered_days、missing_days、coverage_ratio 等字段。 默认稳定趋势门槛分别为周 3 天、月 14 天、年 90 天。 缺样本时返回有限摘要及 insufficient_evidence 提示。 当前实现仍会先调用一次模型，再输出受约束的确定性摘要。 所以 generation_mode=deterministic 不保证“本阶段没调模型”。

Entity、场景和规律字段会按代码规则跨来源合并。 不能只读 digest 来理解周期日记覆盖和成员内容。

家庭画像会先读取用户全部设备的主档，不只读取本次设备。 数量估计优先参考同帧最大并发，降低实体碎片被重复计数的影响。 外观描述和物种判断可按预算调用图片或文本模型。

随后 _annotate_vehicle_categories() 批量读取车辆 semantic 与 appearance。 文本模型给出类别，_build_vehicles() 优先按该类别聚合。 失败或缺失类别时，回退语义类型到车辆类别的词表映射。 VEHICLE_CATEGORY_LLM_ENABLED 默认开启，独立模型默认空。

车辆类别先写在本次内存实体副本，再进入家庭画像。 此函数没有把新类别单独回写 Entity 主档。 归类可扫描全部车辆，入画像仍受默认 10 个活跃日门槛限制。 类别只检查非空并截取 10 字符，没有固定类别枚举校验。

画像还保存 source_day、builder_version、统计量及 species_prior_text。 跨设备汇总不等于已经实现跨摄像头同一身份的可靠匹配。

Chat 记忆怎么进入同一套沉淀？ 当前 prepare 固定不生成 chat，writer 在 pipeline 中也只写 vision。 聊天须由外部生产者写入聊天来源，或推送标准化 observations。 然后经过来源修订、日级 Job 和 R2 Writer。

R2 日日记保存 conversation_segments、user_memories、open_threads。 它也保存 source_coverage、assistant_commitments、corrections 和 digest。 user_memories 中 memory_type 可为 fact、preference、constraint、decision、plan。 计划到期信号可以进入主动感知，但不会自动替用户执行计划。

当前运行范围不是严格的单用户边界。 来源读取按本次设备过滤，但 Job 领取没有本次用户条件。 consolidate_all() 遍历已有日记租户，导出也包含全库数据。 新增设备还可能遇到固定 source_id 的共享 checkpoint。 这些边界决定“本次拉了谁”和“本次加工了谁”可能不同。

最后生成哪些成果，如何交给调用方

Memory 查询是读取阶段，不是再次加工阶段。 pipeline 的 journal 模块在处理后立即调用 assemble_memory()。 默认 vision 为每个指定设备生成一份，再生成用户级投影。 如果选了 chat，还会生成一份用户级 Chat Memory。 其他调用方也能随后通过 FC Memory 接口按需读取。

请求通常包含 user_id、domains、device_sn、as_of、purpose、token_budget。 当前一次请求只处理一个域，不会自动把 vision 与 chat 混成一个包。 vision 缺少 device_sn 时，走用户级多设备投影。 chat 的外部请求不传 device_sn，内部使用 _。

查询按 as_of 选择在该时刻前已经生成的日记修订。 prefer_fresh 偏向新版本，prefer_complete 偏向完整 final 版本。 默认取不超过 7 个日级、4 个周级、6 个月级、2 个年级条目。 不是只按这些数量去查询原始视频。 它读的是已经生成的记忆版本。

cold 时近期细节通常只用最近一日日记，并抑制长期摘要。 warming 时长期摘要需要满足周期趋势覆盖条件。 ready 时才能输出有稳定证据支持的时段模式。 预算裁剪主要按字符估算 token，不是模型 tokenizer 的精确计数。 用户投影会保留每设备边界，不把设备实体自动合并为一个身份。

Memory 包不是所有中间数据库表的完整导出。 场景、家庭主档和 attention 也不会全部自动成为 context 顶层字段。 例如家庭画像先验有独立的 query_user_prior() 接口。 主动感知可通过 FC 的 perceptions 查询读取。 家庭先验、独立规律和实体 timeline 当前只有 FastAPI 对应路由。 不能假定现有 FC HTTP 入口已经暴露全部成果。
