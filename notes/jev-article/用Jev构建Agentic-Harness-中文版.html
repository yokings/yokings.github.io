引言写代码之前：先让决策成形

起点很朴素：我想要一个会不断变好的编码智能体，而且我想知道它变好时到底改变了什么。这个系统仍然需要选择一个模型并限制它的工具范围。然后它需要复核这个选择、并判断结果。Jev 工程正是从这里进入——给系统一个你能检视的选择，然后保留足够的证据来判断这个选择是否真的有帮助。

每一个有用的决策都需要三样东西：

  • 命名好的选项；
  • 代码可以校验的结果；
  • 事后发生了什么的记录。

最后一条很重要：多出来的一次模型调用，仍然得证明自己的价值。本文分四个部分：Jev 如何作为决策层被使用；为什么编码 harness 是放置它的好地方；keel 里构建了什么；以及“自我改进”应该意味着什么（以及它还没有证明什么）。贯穿全文的那句话是：

模型可以建议下一步动作。
但动作的所有权仍归宿主。

这个区别听起来很小。它改变了整个架构。

01 / How Jev Is UsedJev 如何被使用：一份小而清晰的职责

在这次构建中，Jev 从宿主准备好的列表中做选择。“宿主”指的是模型周围的应用代码——在 Jev 有发言权之前，是这段代码决定哪些选项可用。它返回一个类型化的、固定且可校验格式的结果，含义是“选这个”或“我无法选择”。这就是全部的契约。

宿主准备菜单；Jev 从中挑选；宿主再复核一遍这个选择。

保持接口狭窄有一个很实际的理由：如果你允许模型返回任意指令，那么应用中每一个调用它的部分，都得自己想办法理解那条指令究竟是什么意思。固定格式让这份工作变得愉快地无聊——读取结果、对照当前状态校验、接受它，或者启用回退。一个好类比是：繁忙车间里的调度员可以决定哪个工位接哪件活儿，但不能悄悄改写锯子的安全规程。

选择器可以介入的两个位置

1）为新任务选择路由。当一个全新的任务没有固定的 provider 或 model 时，宿主准备出符合条件的候选；Jev 或本地 Laya 在其中挑选，或者弃权。固定路由、进行中的会话、恢复的会话，都会被原样保留。

“挑一个最好的模型”需要一个边界：宿主必须准备好运行它所给出的每一个选项，所以要在 Jev 看到它们之前先做筛选——移除未安装或未启用的 provider、找不到的模型、不支持的推理等级。（provider 仍会在会话开始时检查自己的登录状态，即使某个路由通过了宿主的检查，这一步依然有可能失败。）

2）在 DeepSeek 循环中选择下一步。循环提供四个焦点选项：

  • inspect检查
  • implement实现
  • verify验证
  • answer回答

每个选项都映射到一组由宿主定义的工具包。选择器返回一个焦点 id；宿主找出它被允许的工具，然后在使用前再对照当前的工具定义校验一遍。“回答”是个好例子——它不获得任何工具。如果选择器说“回答”，系统不会塞给它一个 shell 然后指望它守规矩；被允许的工具包是空的，因为在这里，“回答”本来就是这个意思。

一个小例子能说明这种分工：让应用去修一个解析器的 bug。固定的 provider 保持固定；对于一个启用了自动选择、全新的未固定任务，宿主给出符合条件的路由——选择器在这个列表里挑选，它没法凭空召唤出一个缺失的 provider。之后，在内嵌的 DeepSeek 循环里，决策变得更小：选择 verify 会改变被放行的工具包——但这并不能证明补丁是正确的；仍然必须有一次检查真的跑起来，而且它的结果仍然得有意义。设计在这里就对上了：“用哪个 worker？”和“下一步用哪些工具？”值得拥有彼此独立的边界，因为它们是不同的活儿，有不同的失败模式。

重要的边界：外部智能体保留它们自己的循环

keel 可以通过 Agent Client Protocol（ACP）承载多个编码 provider。这些 provider 运行着各自的工具循环，并且可能暴露出针对工具、上下文大小或交接的控制项。但在这次构建中，Jev 和 Laya 并不接管那些内部机制。原因是实际的：我们能读到 provider 的能力描述，但一段描述本身，并没有给宿主一条真正去执行该动作的途径——一个被列出来的斜杠命令，不会自动变成 Jev 可以调用的动作（在当前路径下，一个斜杠命令可能只是变成发给 provider 的提示词文本）。

在架构图上再画一根箭头，并不会凭空造出一个 API。边界应当沿着我们能控制的代码来划。

实际运行中是三层：宿主、决策层，以及可能存在的、由 provider 自有的智能体循环。宿主可以把一个新任务路由给某个 provider——但这并不能说明谁控制着该 provider 的下一次工具调用。keel 的能力审计（列出命令、技能、模式和工具）有助于划出这条线。

一个相邻的接触面是 computer use：keel computer-use decide 让 Laya 或 Jev 选择一个由宿主准备好的低风险动作 id，或者弃权——但这个命令并不执行桌面动作。“提议一个点击”和“真的去点”是两件不同的责任。兼容的 ACP 智能体可以通过 MCP 使用已安装的桌面工具；这些智能体依然拥有自己的内部循环。

选择与许可是两件不同的事

Jev 可以挑选一个候选。它不能批准一个危险动作。需要许可的工具走正常的权限流程；在应用要求的地方，用户批准依然适用。模型选择不授予权限，高置信度数值同样不授予。

行动之前，再查一次状态

在应用一个选择之前，宿主会检查这个动作是否仍与当前任务状态相符；如果 provider 列表变了，或路由已经过期，它可以拒绝并回退。在 DeepSeek 循环内部，被指名的工具在运行之前还会被再校验一次。两处检查服务于同一个目的：不让一个旧决策作用在一个已经变了的系统上。

“这才是无聊的部分。安全检查就该要这种无聊。”

给不确定性一条明确的出路

“我无法选择”是一个有效结果。宿主仍然需要知道接下来该做什么。在调用选择器之前就定义好回退方案，然后记录它何时被用到——这样回退就不会被算成选择器的功劳。在校验结果并观察结果之后，宿主会写入一个决策事件或回执，让我们能够问出一些很普通的工程问题：候选有哪些？选择器是选了还是弃权了？校验接受了吗？发生回退了吗？随后出现了什么工具结果？

重要 这些记录不是私密的思维链。模型的解释并不能证明事情为何发生。

02 / Why a Coding Harness为什么要把它放进编码 Harness？

人们谈论编码智能体时，常常说得好像它只是一次调用：提示进去，补丁出来。真实的工作更像一连串分叉：

  • 这个任务该由哪个模型处理？
  • 智能体应该先检查文件，还是直接开始编辑？
  • 现在哪些工具是相关的？
  • 在决策“飞行的”这段时间里，仓库变了吗？
  • 系统应该重试、弃权，还是去问人？
  • 改动编译通过了吗？通过那些针对性的检查了吗？保住用户的意图了吗？

这些决策的成本各不相同：在一个小小的重命名上用慢模型是浪费时间；而一个错误的选择，可能比一个慢选择代价更高——快模型在大型迁移中可能需要更多次重试；一个工作区里无害的工具选择，在另一个工作区里可能后果显著。Harness 持有那些塑造每次动作的细节：当前仓库状态、可用的 provider 与工具定义、权限与任务状态、检查的结果。模型只是这个系统的一部分。它不是这个系统。

一个独立的决策 demo 可以展示模型在三个标签之间做选择，但它不会告诉你这个选择是否可用。在编码 harness 内部，宿主能回答具体的问题：这些选项当时真的可用吗？任务是全新的、固定的，还是已经在跑了？被选中的工具在执行开始时还存在吗？权限层允许这个动作吗？返回了什么结果？验证发现了回归吗？

作者的立场很直白：把选项、选择和结果给我看。没有这些，所谓“智能体变好了”基本就是感觉。

三种模式，三种不同的选择

Laya 和 Jev 是彼此独立的选择器；Normal 模式跳过选择。Core ML 是 Apple 的本地模型运行时；Jev 使用机器上已有的受保护凭据，在这次构建中没有输入密钥的界面。“总是用最聪明的模型”无视了延迟、隐私、凭据和用户意图——模式选择给了这些权衡在应用里安放的位置。

多出来的调用，必须挣回自己的位置

一个重要的岔路：路由可能变成它自己的小官僚机构。如果挑一个 worker 花的时间比任务本身还长，我们就做出了一个非常精致的候车厅。真正该比的，是任务的总成本：选择器耗时、worker 耗时、重试，以及审阅投入。

一次更便宜的决策调用，只有在整个活儿受益时才有用。本文还没有用编码基准测试证明这份回报。还有一个明摆着的限制：选择器没法挑一个宿主忘了提供的选项。

一个好的 harness 会在“决策”和“执行”之间划一条硬线：对于路由选择，模型拿到的是候选 id——指向宿主准备好的选项的标签；这些 id 不允许模型凭空造出一条新命令或一个新 provider。在 DeepSeek 循环内部，选择器返回一个焦点 id，宿主把它变成一组具体的、被允许的工具，然后再校验一次。这意味着决策层是可替换的——调用方不需要信任它的说法，只需要信任宿主的检查；而这些检查必须清楚到可以被检视。这就是这个小小接口之所以讨喜：你可以指着那个做出的确切选择，以及它放行的确切工具集。给它更多自由，你也同时增加了更多“需要在运行跑偏时解释”的行为。

与此同时，harness 应当保留那些麻烦但重要的部分：把弃权显示出来，把对过期动作的拒绝记录下来，把回退到用户原始路由的情况记录下来。这些细节让我们能够追溯：宿主提供了这些选项 → 选择器返回了这个 id → 宿主依据这些规则接受或拒绝了它。

诚实需要对应的那一半 把决策层放进 harness 并不会让每个结果都正确——它只是让边界更容易说清，让结果更容易检视。它并不能证明 Jev 选了最好的模型，一次成功的构建也不是选择器带来的。还有，“本地 Laya”描述的是选择器——你的编码 worker 仍然可能调用一个托管模型，一个本地运行的 ACP 客户端同样如此。在把整个工作流称作本地或私密之前，先把每一跳都追一遍。

03 / What We Built我们构建了什么：keel 0.2.0

这次构建是 keel 0.2.0，一个本地优先的 Mac 编码应用：

  • 基础：一个源自 Avid 的编码工作区
  • 语言：Rust
  • 界面框架：GPUI
  • 平台：Apple Silicon，macOS 15+

这个细节之所以重要，是因为故事里有两类工作：应用本身——一个真实的编码工作区，带着会话、provider 连接、工具和本地决策模式——以及 Jev 工程的研究与评测材料。它们相关，但不是同一个交付物。工作从一个能跑起来的编码环境（任务、仓库、provider 会话、工具）出发，这给了它一个实际的中心：决策在挂到任务、仓库、provider 会话和工具执行上时，会是什么表现。

设计过程：让选择保持可读

有用的设计问题很简单：Jev 可以在哪里做出一个应用仍然能够校验的选择？这个问题既标定了它该待在哪里，也解释了为什么在宿主无法强制执行结果的地方就停下。五个步骤：

  1. 识别决策边界。新任务路由和有界的下一步焦点都是可行的；provider 内部动作则不是，因为宿主并不拥有那些循环。
  2. 让选项显式化。宿主知道哪些 provider 和模型已安装、已启用且有效。选择器接收候选；它不编造候选。
  3. 保留用户意图。固定的路由保持固定；正在运行的会话不会被悄悄改道。全新的、未固定的工作，才是自动路由选择该待的那个狭窄位置。
  4. 构建常规路径。本地 Laya 是默认；Jev 是一个刻意的 opt-in；Normal 模式为已有的路由行为保留。
  5. 为失败设计一个形状。格式错误的输出、无效的 id、过期的任务详情，以及弃权——各自都有清晰的结果：拒绝、回退，或询问用户。没有人需要假装每个模型响应都是可用的。

保守？当然。

我宁愿要一个我能调试的狭窄选择，也不要一个我没法在代码里追溯的漂亮承诺。

Jev 在请求路径中的位置

用直白的话说，路由路径有八步：

  1. 一个新任务到达，没有显式的固定路由；
  2. 宿主读取当前 provider 和模型的可用性；
  3. 它构造出一个有限的、符合条件的候选列表；
  4. 所选的决策模式调用本地 Laya 或托管的 Jev（如果已启用）；
  5. 选择器返回一个候选 id，或者弃权；
  6. 宿主检查该选择是否仍然合格、且是当前有效的；
  7. 应用启动该路由，或按策略回退；
  8. 一条决策记录捕获所发生的一切。

固定路由和已有会话会绕过自动选择——这不是脚注，而是一条核心的产品规则。步骤选择器有它自己的检查：宿主提供焦点 id 和候选工具集，选择器返回一个焦点，宿主依据当前的工具 schema 重建工具包，并在派发时再次校验那个被指名的工具。同样的原则，不同的生命周期。

04 / What “Self-Improving” Should Mean“自我改进”应该意味着什么

已发布的应用会记录决策，但它不会自我训练

这是需要守住的那条线：keel 记录选择器的活动和结果，能够支撑评测，但它不会自动从聊天历史里训练 Laya，也不会在一次失败的运行之后悄悄重写自己的策略。这次发布并没有证明一个科幻意义上的自我改进智能体。

它给出的是反馈回路的起点：一个回执可以变成一个场景；一个场景可以针对改过的提示词、策略或模型重放；一个人可以审阅差异，并决定是否保留这个改动。没那么炫酷，是——但它可行：一条改动的规则、一个旧结果、一个新结果。“智能体学到东西了”只会让你猜。

把一次失败，变成一个你还能再跑的案例

假设一个路由选择器选中了一个转瞬即逝就不可用的 provider。别只是说“Jev 搞糊涂了”——把细节存下来：提供了哪些选项和任务状态、选中的 id、宿主的校验结果、用到的回退。然后创建一个可重放的场景：

  1. 复现同样的候选集和任务标记；
  2. 运行基线选择器；
  3. 在相同条件下运行候选改动；
  4. 比较有效选择、弃权、回退、延迟和下游结果；
  5. 由人来审阅这个改动是否改善了预期行为。

对于工具焦点的选择，情况有所不同：模型选中了一个在派发前 schema 就已经变了的工具包——检查重建工具集时是否把旧工具过滤掉了，以及如果仍然被请求，宿主是否会拒绝它。

结构化记录的价值在于，它给了你重建那个决策的条件。“智能体看起来有点糊涂”给你的只是一种情绪。

与普通 harness 对比：信用分配

一个通过了的任务，并不能告诉我们该把功劳记给哪个组件——也许 worker 在原始路由上本来就能解决它。保持任务集和评分规则固定；对 worker、提示词、仓库或审阅者的改动，同样会影响结果。最终对比要用一个单独的任务集——不要在每个用例上调完参，再把熟悉的那些当作证明。那次难看的运行，可能暴露出一条干净演示所掩盖的缺失规则。记录失败、回退率、总耗时和审阅投入。

作者明确表示 这是一个提议中的评测设计；本文并未声称有任何实测的编码质量提升。

给生产变更留一道人工闸门

一个改进回路可以对以下东西提出变更：候选构造规则、选择器提示词或类型化 schema、回退策略、本地模型或托管路由，以及挂在某个焦点选择上的工具包。对于每一项变更：保留旧版本、重放相关场景、检查回归，然后由一个人来批准成为新基线的那个版本。

不做静默的自我训练；不接受那种“它变了，因为它学会了”却既没有 diff、也没有回滚路径的说法。

Where to Start从哪里开始

从一个宿主能够校验的选择开始。记住六条规则：

  • Jev 可以在宿主准备好的选项中挑选；它并不拥有宿主；
  • Laya 和 Jev 是彼此独立的模式，不是同一个模型的两个名字；
  • provider 自有的内部循环，仍然归 provider 所有；
  • 选择不授予权限；
  • 记录支撑的是未来的评测回路；它们并不意味着应用会训练自己；
  • 公开的 Jev 工程仓库包含框架与示例；keel 是这里讨论的那个应用构建。

如果你在构建一个编码 harness，把这四件事写下来：

  • 它被允许做出的一个决策；
  • 它能看到的精确选项；
  • 当它弃权时，会发生什么；
  • 你将如何知道结果是否有帮助。

然后构建最窄的那条路径，去证明这些规则。

把起点放得足够小，让一个糟糕的选择无处藏身。
