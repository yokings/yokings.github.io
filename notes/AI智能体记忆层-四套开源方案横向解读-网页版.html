2026 年新记忆算法的五条设计原则

FIVE PRINCIPLES · arXiv:2504.19413
核心判断：记忆的难点不在「存」，而在「事后还能以正确的方式被找到」
ADD

Single-pass ADD-only　一次 LLM 调用完成抽取，不做 UPDATE / DELETE

记忆只累积、不覆盖。冲突不在写入时裁决，而留给检索时的时间推理去判断「哪条才是最新的」。

AGT

Agent-generated facts 一等公民　Agent 自己确认过的动作，与用户说的话同等权重入库

避免「只有用户说过的才算数」造成的记忆缺失：Agent 执行结果、工具返回值同样是事实来源。

ENT

Entity Linking　事实中的实体被抽出、向量化，并跨记忆互相链接

把扁平事实串成一张松散的实体图，让「张三的技术栈」这类跨事实问题有路可走。

SIG

Multi-signal Retrieval　语义 + BM25 关键词 + 实体匹配并行打分后融合

单靠向量会漏掉精确词面匹配（如专有名词、型号），单靠关键词又受不了同义改写；三路互补。

TMP

Temporal Reasoning　带时间维度的检索，区分当前状态 / 过去事件 / 未来计划

这是 ADD-only 能成立的前提：既然不覆盖旧记忆，就必须能在检索时分辨「曾经是」和「现在是」。

为什么是 ADD-only？　传统做法在写入时做 UPDATE：新信息到来 → 找到旧记忆 → 改写它。问题是「改写得对不对」当场无法验证，一旦改错，原始信息永久丢失。Mem0 的做法：全部追加，保留完整时间线，把「以哪条为准」推迟到检索阶段，用时间推理裁决。代价是存储膨胀与去重压力，收益是可追溯、不会误删。
论文与工程的关系　Mem0 有正式论文（arXiv:2504.19413），但产品化的优先级高于学术复现：README 明确说明公开基准分数来自其托管平台（含专有优化），开源 SDK 与之存在差距。选型时要把这个差预期算进去。

时序上下文图的五条设计原则

FIVE PRINCIPLES · TEMPORAL CONTEXT GRAPH
核心判断：记忆的难点不在「记住」，而在「事实变了以后，还能说清什么时候是什么样」
TMP

Temporal Validity　每条事实都带有效窗口：何时成为真、何时被取代

ONT

HYB

每个方案都有需要提前知道的坑

RISK REGISTER · READ BEFORE ADOPTING
这些是在选型评审会上最该被问到的问题
Mem0

公开基准成绩来自托管平台，含未开源的专有优化，开源 SDK 实测会有落差；ADD-only 意味着记忆只增不减，长期运行需自行规划去重与归档策略。

Hindsight-CN

仓库仅 13★，由个人维护的中文发行版，价值高度依赖上游 vectorize-io/hindsight；若上游重构 API，中文版同步可能滞后。

Zep / Graphiti

getzep/zep 已转型为「示例与集成」仓库，真正的引擎在 getzep/graphiti（31,081★），旧的 Community Edition 已废弃；自托管必须自带图数据库（Neo4j 5.26 / FalkorDB / Neptune，Kuzu 已废弃），运维成本高于 Mem0；摄入强依赖 LLM 稳定的结构化 JSON 输出，本地小模型易抽取失败；Zep Cloud 的 sub-200ms 是托管版口径，自托管性能取决于你自己的部署。

Honcho-CN

仓库仅 6★ 且自 2026-05 起未再更新，属个人适配版，长期维护性存疑；推理深度换来的代价是延迟与成本，且 Dream 必须异步跑通才有意义。

T-Mem

本质是离线评测流水线而非在线服务；构建阶段 LLM 调用密集（401 条对话的 LoCoMo-Plus 全量构建需关注并发与费用），落地生产要自己补上在线读写层。

通用问题

四个项目的评测分数来自不同协议：QA 模型、judge 模型、数据集、提示词各不相同，绝不可直接横向比较绝对值。本演示中的对比仅用于说明机制差异。

给决策者的一句话　这四个项目都还处在快速演进期。真正的风险不是「选错」，而是把业务逻辑与某个特定 SDK 深度耦合而不留抽象层 —— 建议始终通过一层自己的 Memory 接口封装，保证可替换。
